02Las 3 fases de la estrategia

Cada fase entrega valor incremental con criterios de "done" medibles.

Fase 1 · Adapter

MVP funcional end-to-end

Duración estimada: 1–2 semanas

Los 12 stubs FDE se convierten en adapters que llaman al legacy y transforman el shape. El .agent se alinea con contracts reales. Cero código nuevo con reglas de negocio.

  • Adapters delgados llaman al Apex legacy existente
  • Alineamos outputs del .agent a los reales
  • Preview live-actions con 15–20 escenarios reales
  • Publish + Activate como agente paralelo (V40 intacto)
Ownership: 100% del .agent + 22 adapters
Fase 2 · Reemplazo

Migración gradual con tests de paridad

Duración estimada: N × 1–2 sem/acción

Cada adapter se reemplaza por una implementación propia, action por action, con tests de paridad como puerta de calidad medible antes de cortar el adapter.

  • Documentar exhaustivamente el comportamiento del legacy
  • Escribir tests de paridad (legacy vs. FDE-impl para N inputs)
  • Implementar BW_FDE_* propia con SOQL + callouts directos
  • Cortar el adapter solo si paridad = 100% o hay delta documentado
Ownership por acción: 100% al pasar la puerta
Fase 3 · Deprecación

Legacy fuera del stack (opcional)

Duración estimada: Al cabo de N sprints sin uso

Cuando todas las actions corren sobre FDE, se coordina con Betterware la deprecación formal del legacy. Un solo lugar para bugs, features y evolución.

  • Verificar cero consumers de las clases legacy
  • Marcar como @deprecated con puntero al reemplazo
  • destructiveChanges.xml las remueve del org
  • Documentación cierra: un solo stack para el agente
Ownership: 100% del stack del agente

06Riesgos — mitigados vs. introducidos

Cómo el híbrido mueve la aguja del riesgo comparado con los extremos.

Mitigado
Divergencia silenciosa
Los tests de paridad exponen inmediatamente cualquier desviación entre la implementación FDE y el legacy.
Mitigado
Feature debt oculta
Documentación exhaustiva antes de reemplazar cada acción — nada se migra sin entenderlo primero.
Mitigado
Bug reports confusos
Single-owner por acción después de Fase 2. Ownership matrix documentada desde día 1.
Mitigado
Scope creep
Fases discretas con criterios de "done" medibles evitan expansión no controlada del alcance.
Introducido
Complejidad temporal en Fase 2
Durante la migración de cada acción coexisten dos clases (adapter + impl). Naming discipline crítica.
Introducido
Costo total mayor que adapter puro
Fase 1 + Fase 2 suman ~5–8 semanas. Se mitiga por entrega incremental — el valor de Fase 1 llega en 1–2 sem.
Introducido
Requiere disciplina de tests de paridad
Sin tests robustos en cada migración, se pierde la garantía de comportamiento equivalente.
